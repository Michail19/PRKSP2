# Практическая работа №6 — Solidity и Remix IDE

**Тема:** смарт-контракт жизненного цикла доставки.  
**Среда:** [Remix IDE](https://remix.ethereum.org/) → Remix VM (локальная тестовая сеть в браузере).  
**Язык:** Solidity `^0.8.20` (например, компилятор 0.8.30/0.8.33, если доступен в Remix).  
**Связь с BootcampLabs:** тестовые номера заказов/доставок и дарксторов из АС сервиса доставки; никакой реальной БД, backend, криптокошелька или средств оплаты не требуется.

## Суть модели

Сведения о доставке:

- `deliveryId` — ID записи внутри смарт-контракта (начинается с 1);
- `orderId` — ID заказа в исходной АС (для простоты один orderId соответствует одной доставке);
- `darkstoreId` — ID даркстора из BootcampLabs;
- `customer` — `address` пользователя, вызвавшего `createDelivery`;
- `courier` — `address` назначенного курьера (сначала `0x000…000`);
- `priceKopecks` — цена в **копейках** (например, 40 399,28 ₽ = `4039928`);
- `status` — состояние `enum`;
- `createdAt` — время создания блока `block.timestamp`.

Роли:

- **Оператор** — аккаунт, развернувший контракт. Единственный может назначать курьера.
- **Клиент** — аккаунт, создавший доставку. Может отменить её до начала доставки.
- **Курьер** — назначенный адрес. Только он может принять, начать и завершить доставку.

Состояния `enum Status`:

| Число в Remix | Состояние | Значение |
|---|---|---|
| `0` | `Created` | Создана |
| `1` | `Accepted` | Принята курьером |
| `2` | `InTransit` | В пути |
| `3` | `Delivered` | Доставлена |
| `4` | `Cancelled` | Отменена |

Разрешённые переходы:

```text
Created --acceptDelivery--> Accepted --startDelivery--> InTransit --completeDelivery--> Delivered
   |                                
   +--cancelDelivery--> Cancelled    
                          ^          
Accepted --cancelDelivery--+         
```

`assignCourier()` **назначает адрес курьера, но не переводит доставку в `Accepted`**. Это отдельный осознанный шаг: назначенный курьер должен сам подтвердить принятие. `InTransit` и `Delivered` — терминальные относительно отмены, `Cancelled` и `Delivered` — окончательные статусы.

## Подготовка Remix IDE

1. Откройте **https://remix.ethereum.org/**.
2. В панели **File Explorer** создайте папку `contracts`, затем файл `contracts/DeliveryLifecycle.sol`; скопируйте код одноимённого файла из архива. Можно также загрузить файл в рабочую область Remix.
3. Откройте **Solidity Compiler** и выберите установленный компилятор версии **0.8.20 или новее из семейства 0.8.x**, подходящий под `pragma ^0.8.20`. Скомпилируйте `DeliveryLifecycle.sol`.
4. Откройте **Deploy & Run Transactions**, выберите **Remix VM** (не Browser Extension или реальную сеть), аккаунт **account-0** и контракт `DeliveryLifecycle`.
5. Нажмите **Deploy**. Аккаунт `account-0` станет оператором. На Remix VM используются тестовые адреса и тестовые ETH; платить или подключать MetaMask не требуется.

> Если Remix показывает названия сред `Remix VM (Cancun)`, `Remix VM (Prague)` или другие — можно выбрать доступный локальный вариант. Интерфейс Remix иногда меняется.

## Ручной сценарий выполнения (для скриншотов)

В выпадающем списке `ACCOUNT` сохраните адреса 3 тестовых аккаунтов. Номера могут отображаться по-другому, важны **три разные адреса**:

- `account-0` — **operator** (деплой);
- `account-1` — **customer** (создание/отмена);
- `account-2` — **courier** (принятие/движение/завершение).

Ниже значения параметров указываются **по порядку аргументов функции в Remix**.

### Сценарий A — успешная доставка

1. Переключитесь на **account-1**.
2. Вызовите `createDelivery(1, 3, 4039928)`. Это заказ/доставка №1, даркстор №3, стоимость **40 399,28 ₽** из предыдущих практических. В логах появится событие `DeliveryCreated`.
3. Вызовите `getDelivery(1)`: статус `0 (Created)`, `courier = 0x0000000000000000000000000000000000000000`.
4. Переключитесь на **account-0**. Вызовите `assignCourier(1, <адрес account-2>)`; в логах событие `CourierAssigned`.
5. Переключитесь на **account-2**. Вызовите `acceptDelivery(1)` → статус `1 (Accepted)`.
6. Вызовите `startDelivery(1)` → статус `2 (InTransit)`.
7. Вызовите `completeDelivery(1)` → статус `3 (Delivered)`.
8. Вызовите `getDelivery(1)` или `getStatus(1)`, откройте детали транзакций и `DeliveryStatusChanged` в терминале.

В Remix при отправке транзакции функция `createDelivery()` возвращает `deliveryId` через `return`, но этот return может не отображаться так же удобно, как результат read-only вызова. Используйте `getDeliveryCount()` и события, чтобы увидеть ID.

### Сценарий B — запрещённый переход

1. **account-1**: `createDelivery(2, 2, 10000)` → создаётся ID `2` со статусом `Created`.
2. **account-0**: `assignCourier(2, <адрес account-2>)`.
3. **account-2**: вызовите `completeDelivery(2)` **до** `acceptDelivery(2)` и `startDelivery(2)`.
4. Remix покажет **revert** (ожидаемо): `InvalidStatusTransition(Created, Delivered)`; статус остаётся `0`.

### Сценарий C — запрет отмены после начала

1. **account-1**: `createDelivery(3, 5, 15000)`.
2. **account-0**: `assignCourier(3, <адрес account-2>)`.
3. **account-2**: `acceptDelivery(3)` и `startDelivery(3)`.
4. **account-1**: вызовите `cancelDelivery(3)` — **revert** (недопустимая отмена в статусе `InTransit`).

### Сценарий D — права пользователя

Создайте ещё одну доставку, назначьте курьера (account-2), затем попытайтесь вызвать `startDelivery(id)` от **account-1**: получите ошибку `OnlyAssignedCourier`. Также назначение курьера с любого адреса, кроме **account-0**, завершится `OnlyOperator`.

### Сценарий E — допустимая отмена

Создайте ещё одну доставку, назначьте и примите её, затем **account-1** вызывает `cancelDelivery(id)` до `startDelivery`. Статус становится `4 (Cancelled)`. Повторный вызов перехода в `InTransit` должен отклоняться.

## Запуск unit-тестов в Remix

1. Создайте `tests/DeliveryLifecycle_test.sol` и скопируйте содержимое файла тестов.
2. В **Plugin Manager** найдите **Solidity Unit Testing** (или `Unit Testing`) и включите плагин.
3. В панели тестирования выберите папку `tests` (плагин может попросить выбрать/создать каталог).
4. Выберите `DeliveryLifecycle_test.sol` и нажмите **Run**.
5. Ожидаемый результат: **12 положительных тестов**, включая проверку запретов через `try/catch`. Это **ожидаемый** результат, который нужно подтвердить запуском в Remix.

Примечание: специальный импорт `remix_tests.sol` поддерживается **плагином тестирования Remix** и не обязан успешно собираться обычным `solc` без инструментария Remix.

Тесты проверяют:

- создание, чтение полей и начальный статус;
- полный путь `Created → Accepted → InTransit → Delivered`;
- запрет `Created → Delivered`;
- запрет `Created → InTransit`;
- назначение только оператором;
- начало работы только назначенным курьером;
- разрешённую отмену до движения;
- запрещённую отмену после начала;
- отмену только клиентом;
- запрет одинакового `orderId`;
- запрос несуществующей доставки;
- запрет повторного завершения.

## Что важно понимать перед защитой

- **`msg.sender`** — адрес вызывающего аккаунта/контракта; на его основе проверяются роли.
- **`mapping`** хранит записи по ключу, а `struct` объединяет поля одной доставки.
- **`enum`** даёт типизированные состояния. Числа `0–4` — кодирование этих состояний в ABI.
- **`event`** записывает сведения об операциях в журналы транзакций; не является механизмом проверки прав.
- **`revert`** отменяет изменения состояния в неуспешной транзакции (потраченный gas обычно не возвращается в настоящей сети).
- **Цена** задаётся в копейках, это демонстрационное поле. Контракт **не переводит ETH и не принимает платежи**.
- **Отсутствуют** настоящие персональные данные, геолокация и подключение к backend/BaaS; контракт демонстрирует строго ограниченную логику контроля состояний.
- **Ограничение примера:** оператор централизован (один адрес), а создание произвольного `orderId` открыто всем. Для production потребуются подтверждение заказов из backend, управление ролями, безопасная интеграция (oracle/relayer), аудит и ограничения доступа к чувствительным данным.
