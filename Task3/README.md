# Практическая работа №3 — реактивная обработка данных АС Поставщиков (RxJava 3)

## Цель

Реализовать реактивную обработку данных, опираясь на фактическую модель BootcampLabs:

- `darkstore (id, address)` — дарксторы;
- `good (id, name, price)` — товары;
- `delivery (id, id_darkstore, datetime_delivery, status)` — доставки;
- `goods_list (id_good, id_delivery, count)` — позиции доставок.

**Не используются** API/логины/пароли Kintsugi, Pangolin или Keycloak; реальная база данных не требуется.

### Исходные данные

Точно перенесены значения из предоставленных SQL INSERT-запросов:

| Файл | Записи |
|---|---:|
| `data/darkstore.csv` | 5 |
| `data/good.csv` | 10 |
| `data/delivery.csv` | 20 |
| `data/goods_list.csv` | 30 |

Важно: исходные INSERT не задают первичные ключи, поэтому ID в CSV предполагаются 1, 2, 3 ... в порядке INSERT в пустые таблицы с автоинкрементом. Если реальные ID в вашей БД другие, их потребуется синхронизировать.

Поля с запятыми (адреса) и кавычками (названия товаров) записаны корректно с CSV-экранированием.

## Алгоритм работы

```
4 исходных CSV
    ↓
Flowable.fromIterable(30 goods_list записей)
    + Flowable.interval(временные новые события)
    ↓
subscribeOn(Schedulers.io())
    ↓
observeOn(Schedulers.computation())
    ↓
filter(count > 0)
    ↓
flatMap → сопоставить Good, Delivery, Darkstore
        └─ onErrorResumeNext(Flowable.empty()) для отдельной ошибочной записи
    ↓
filter(status != CANCELLED)
    ↓
map → сумма позиции = price × count
    ↓
вывод отдельной обработанной позиции
    ↓
groupBy(darkstoreId) → reduce(BigDecimal.ZERO, BigDecimal::add)
    ↓
суммарная стоимость позиций для каждого даркстора
```

Список новых событий, создаваемых программой со временем, не изменяет исходные CSV:

- товар №1, доставка №21, количество 3 — корректно;
- товар №9, доставка №22, количество 2 — корректно;
- товар №999, доставка №23, количество 1 — ошибка отсутствующего товара; цепочка продолжает работу;
- товар №3, доставка №23, количество 0 — исключается фильтром;
- товар №6, доставка №23, количество 4 — корректно после двух плохих событий.

В программе также создаются три *тестовые* записи доставок №21–23, связанные с существующими дарксторами. Это демонстрация прихода новых событий, а не изменение данных BootcampLabs.

### Важное уточнение по агрегации

Из общей суммы исключены позиции доставок со статусом `CANCELLED`. Статусы `SUBMITTED`, `ASSEMBLY`, `DELIVERY`, `COMPLETED` учитываются. Поэтому итог — **стоимость позиций неотменённых доставок**, а не фактически полученная выручка. Это учебная трактовка, выбранная для демонстрации `groupBy`.

## Backpressure

Дополнительный пункт задания применим, так как выбран `Flowable`:

- источник создаёт до 400 элементов с интервалом 1 мс;
- обработчик тратит 25 мс на элемент;
- `observeOn(..., false, 8)` ограничивает предвыборку;
- `onBackpressureDrop()` отбрасывает элементы, которые не помещаются в очередь при перегрузке;
- в конце выводятся счётчики **создано / обработано / отброшено**.

Это отдельная демонстрация, не влияющая на данные доставок.

## Что фотографировать для отчёта

1. **Реактивная цепочка:** первая часть консоли, где видны `[SOURCE]`, `[PROCESSED]`, расчёты и товары.
2. **Ошибки и новые события:** кадр с `[NEW EVENT]`, `[ERROR]` для товара `999`, `[FILTER]` для количества `0`, и следующим `[PROCESSED]` — это доказывает, что цепочка не остановилась.
3. **Группировка + многопоточность + backpressure:** вывод `[TOTAL]`, `[BACKPRESSURE]` и разные имена потоков `[RxCachedThreadScheduler-...]` / `[RxComputationThreadPool-...]`. При необходимости разбить на два снимка, но общий лимит обычно 2–4 скриншота.
4. **BootcampLabs:** настоящий скриншот прохождения модуля **«Back-end АС Поставщиков»**. Сгенерировать подлинный скриншот вашего личного прохождения программа не может.

Рекомендуется уменьшить размер шрифта консоли или запустить отдельный `--only-backpressure`, чтобы весь необходимый фрагмент вошёл в кадр.

## Для защиты

- `Flowable`: реактивный поток с поддержкой backpressure.
- `filter`: оставить элементы, соответствующие условию.
- `map`: преобразовать один элемент в другой.
- `flatMap`: из одного элемента получить вложенный реактивный источник и объединить его с потоком.
- `groupBy`: создать группы по ключу (у нас `darkstoreId`).
- `reduce`: накопить одну агрегированную сумму из элементов группы.
- `subscribeOn`: выбрать Scheduler для подписки и upstream-источника.
- `observeOn`: переключить Scheduler для дальнейших операторов.
- `onErrorResumeNext`: заменить ошибочный вложенный источник запасным, здесь пустым.
- `onBackpressureDrop`: при перегрузке отбрасывать избыточные события, вместо бесконтрольного накопления.

## Ограничения учебной реализации

- Исторические данные из CSV фиксированы; новые записи генерируются в памяти через `Flowable.interval()`, а не читаются из сети/БД.
- Для небольшого объёма данных используется простое чтение CSV целиком.
- Расчёт суммы ведётся через `BigDecimal`, чтобы избежать ошибок двоичных `double` на денежных значениях.
